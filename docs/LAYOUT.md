# Карта кода South Park (USA)

Итог этапа 1. Всё получено из самого ROM скриптами `tools/rom_prepare.py` и
`tools/layout_scan.py`; метод взят из `turok2-decomp` (`docs/VRAM-LAYOUT.md`).

## Главное

Схема памяти та же, что в Turok 2 (движок Iguana, «VM» = virtual memory):
код исполняется в useg через TLB, данные и BSS лежат в KSEG0.

| Область | ROM | Адрес | Примечание |
|---|---|---|---|
| Заголовок, IPL3 | `0x0000–0x1000` | — | CIC 6102 |
| Загрузочная заглушка | `0x1000–0x1100` | `0x80000400` | KSEG0, только настройка TLB |
| Движок + libultra, `.text` | `0x1100–~0xA8000` | `0x00200500–…` | useg, `ROM = адрес − 0x1FF400` |
| `.rodata` / `.data` | `~0xA8000–0xC2C00` | `…–0x800C2000` | KSEG0, `ROM = адрес − 0x7FFFF400` |
| BSS | — | `0x800C2000–0x800F3730` | обнуляется заглушкой |
| VM-модуль A | `0xC4000–~0xDB810` | `0x00400000` | useg, подкачивается из ROM |
| VM-модуль B | `0xDC000–~0xF2320` | `0x00400000` | похоже, не используется (см. ниже) |
| Ресурсы | `0xF4000–0x1000000` | — | RNC-блоки с `0x9C9E34` |

Стек при старте: `0x803FFFC0`. `main` — `0x0022BCE8`.

## Загрузочная заглушка

IPL3 кладёт 1 МБ с ROM `0x1000` по адресу `0x80000400`. Заглушка:

1. ставит стек и обнуляет BSS;
2. очищает TLB (записи 30…0);
3. записью 31 отображает `0x00200000–0x003FFFFF` на физические `0x000000–0x1FFFFF`
   (PageMask `0x1FE000`, две страницы по 1 МБ);
4. прыгает в `0x0022BCE8`.

Следствие: адрес `0x002xxxxx` — это просто второй вид на `0x800xxxxx` со сдвигом
`0x7FE00000`. Движок не подкачивается, он целиком в памяти с самого старта.

## Вызовы (`jal`) подтверждают раскладку

- 9776 вызовов ведут в `0x002xxxxx/0x003xxxxx`, 783 — в `0x004xxxxx`.
- В KSEG0 (`0x800xxxxx`) кода нет: libultra слинкована вместе с движком в useg
  (инструкции TLB и `eret` лежат в ROM `0x91DF8–0xA64E8`). В Turok 2 иначе: там libultra в KSEG0.
- 942 из 1671 уникальных целей в движке попадают на пролог функции (56 %, остальное — функции без кадра стека).

## VM-менеджер

Код менеджера: `0x0028FBA0–0x00291254`. Это тот же `engine/Virtual/VMEMORY.C` + `VMASM.S`,
что в Turok 2 (там `VM_Initialize` … `VM_FinishPageJob`, `0x0028D820–0x0028ED10`, имена и
C-код есть в `turok2-decomp`).

- `0x0028FBA0` — инициализация (аналог `VM_Initialize`). Запоминает базу картриджа
  `0xB00C4000` (ROM `0xC4000`) для области `0x00400000`.
- Если памяти больше `0x4FFFFF` (есть Expansion Pak): выделяет `0x16F10` байт и одной
  записью TLB отображает на них `0x00400000` (PageMask `0x7E000`) — модуль грузится целиком.
- Без Expansion Pak — подкачка страницами по требованию через обработчик TLB-промахов.
- `0x00291198` — запись в TLB (аналог `STVM_MapTLB`). Её вызывают `0x0028FBA0`,
  `0x0028FF20`, `0x00290270`, `0x0029093C`.

## Два модуля на одном адресе

С ROM `0xC4000` и `0xDC000` лежат два разных блока кода по ~96 КБ, оба слинкованы на
`0x00400000` (совпадение опкодов 10,6 % — это не копии).

Движок использует модуль A:

- в коде есть ссылка только на `0xB00C4000`;
- из 41 адреса, по которым движок вызывает `0x004xxxxx`, 40 — начала функций в модуле A
  и только 3 — в модуле B;
- модуль B обращается к данным `0x8012xxxx`, модуль A — к `0x8010xxxx`: они собраны под
  разную раскладку данных.

Рабочая гипотеза: модуль B — остаток другой сборки. Проверить на этапе 4 (в рантайме
не должно быть чтений ROM из `0xDC000–0xF4000`).

## Что это значит для рекомпиляции

- Заглушку не рекомпилируем: точка входа рантайма — сразу `0x0022BCE8`, стек выставляем сами.
- Модуль A можно держать в памяти постоянно, как при Expansion Pak. Перекрытия модулей,
  из-за которого в Turok 2 пришлось разносить банки, здесь, по-видимому, нет.
- Нужна трансляция адресов useg в памяти рантайма: `0x002xxxxx` → `0x800xxxxx − 0x7FE00000`,
  `0x004xxxxx` → отдельное окно. Указатели на функции в данных — в виде `0x002xxxxx`.
- VM-менеджер также отдаёт движку окна ROM под данные (в Turok 2 так грузятся звуковые
  банки). Обработчик TLB-промахов рекомпилировать нельзя, его придётся заменить своим кодом.

## Открытые вопросы

- Точные границы `.text` / `.rodata` / `.data` в основном сегменте.
- Что лежит в ROM `0xC2C00–0xC4000`, `0xDAF10–0xDC000` и `0xF4000+` (таблицы, похоже на данные модулей).
- Какие ещё области, кроме кода, движок запрашивает у VM-менеджера.
- В ROM есть только F3DEX/L3DEX; аудио-микрокод ещё не опознан.
