# Символы South Park (USA)

Итог этапа 2: список функций, их имена и первый успешный прогон N64Recomp.

## Как это воспроизвести

Нужны `rom/southpark.us.z64` и, для переноса имён, `rom/turok2.us.z64`
(Turok 2 USA 1.0, SHA1 `fb0400f2…1006f1`) и `references/turok2-decomp`.

```
python tools/find_functions.py southpark.us --out rom/southpark.us.funcs.json
python tools/find_functions.py turok2.us --out rom/turok2.us.funcs.json
python tools/match_turok2.py
python tools/make_symbols.py
external/N64Recomp/build/N64Recomp southpark.us.toml
```

`symbols/names.southpark.us.json` и `symbols/southpark.us.syms.toml` лежат в репозитории,
поэтому для обычной сборки ROM Turok 2 не нужен.

N64Recomp нужно собрать с патчем `n64recomp-patches/0001-jump-table-in-another-section.patch`
(см. ниже).

## Поиск функций (`tools/find_functions.py`)

Символов в ROM нет, границы функций восстановлены из кода:

- цели `jal` — достоверные входы;
- функция кончается после безусловного перехода (`jr ra`, `j`, `b`), если нет
  ещё не достигнутой цели ветвления;
- таблицы `switch` читаются из rodata, чтобы метки `case` после последнего `jr ra`
  остались внутри функции;
- указатели на код в данных и адреса, собранные парой `lui`/`addiu` (колбэки);
- мусор между объектными файлами отличается от кода по декодированию: недопустимые
  инструкции и чтение регистров, которым ещё ничего не присвоено.

Объектные файлы South Park выровнены по 8 байт, у Turok 2 — по 16
(`obj_align` в `tools/games.py`). С неверным значением 49 вызовов попадали внутрь функций.

Проверка на Turok 2, где ответ известен из декомпиляции: найдено 2333 из 2337
функций движка, именованных вручную (99,83 %).

Известные ограничения:

- Функция, на которую нет ни вызова, ни указателя, а перед ней стоит мусор, похожий на код,
  может получить начало на 4 байта раньше. Проявится при запуске как «функция не найдена»
  и чинится записью в `symbols/manual_names.southpark.us.txt`.
- 544 функции движка ни на что не ссылаются. Это мёртвый код либо входы, адреса которых
  вычисляются способом, который инструмент не видит.

## Перенос имён (`tools/match_turok2.py`)

Обе игры собраны одним компилятором из одного движка, поэтому общие функции совпадают
инструкция в инструкцию, если замаскировать то, что подставляет линковщик (цели вызовов,
половины адресов `lui`/`lo`).

| Проход | Найдено | Смысл |
|---|---|---|
| exact | 793 | замаскированный код идентичен и уникален в обеих играх |
| callsite | 98 | вызывается из одного и того же места в двух уже сопоставленных функциях |
| order | 226 | лежит между двумя сопоставленными соседями и похожа по коду |

По областям: системные библиотеки (`0x0029…`, `0x002A…`) опознаны почти целиком,
игровая логика (`0x0020…`, `0x0023…`, `0x0025…`) — на 3–20 %, что ожидаемо: это код
самого South Park. VM-модуль опознан на 11 %.

Менеджер виртуальной памяти получил имена целиком: `VM_Initialize`, `VM_HandleTLBMiss`,
`VM_Alloc`, `VM_ManagerThread`, `VM_ReaderThread` и другие (`0x0028FBA0–0x00291254`).

Имена важны не только для чтения: N64Recomp по именам решает, какие функции libultra
заменить реализацией рантайма. Из найденных в South Park он заменит 57, проигнорирует 124
и переименует 11.

## Патч N64Recomp

N64Recomp ищет таблицу переходов в том же сегменте, что и функция
(`rom = vram + func.rom − func.vram`). У этого движка код слинкован в useg
(`0x002xxxxx`), а rodata — в KSEG0 (`0x800Axxxx`), и такой расчёт выводит за пределы ROM.

Патч ищет таблицу в остальных неперемещаемых сегментах. Сегменты данных объявлены в файле
символов без функций (`.data`, `.virtual_data`) только ради этого.

## Заглушки

Ассемблерный код, который N64Recomp не транслирует (регистры сопроцессора 0, TLB, кэш).
Каждая функция опознана по аналогу в Turok 2 (`turok2-decomp`, `docs/ASM_ORIGIN.md`).

| Функция | Адрес | Что делает | Что с ней дальше |
|---|---|---|---|
| `boot_STVM_MapTLB_tail` | `0x00200500` | хвост записи TLB из загрузочной заглушки | не нужна: вход через `game_entry` |
| `STVM_MapTLB`, `STVM_UnmapTLB`, `STVM_DumpTLB` | `0x00291198…` | запись и чтение TLB для VM-менеджера | заменить своим кодом на этапе 3–4 |
| `__osUnmapTLBAll` | `0x002A0450` | очистка TLB | пустая заглушка достаточна |
| `__osException_handler` | `0x0029E1C0` | обработчик исключений libultra | потоки и прерывания делает рантайм |
| `Debug_SetWatch` | `0x0027D704` | отладочные регистры Watch | пустая заглушка достаточна |
| `SNDebug_*` (7 шт.) | `0x002A51B0…` | отладчик SN64: сброс кэша, дамп TLB и контекста | пустая заглушка достаточна |

## Что осталось на следующие этапы

- **Адреса useg в рантайме.** Сгенерированный код обращается к памяти через макросы
  `MEM_*`, рассчитанные на `0x800…`. Нужна трансляция `0x002…` и `0x004…`, а указатели на
  функции в данных имеют вид `0x002xxxxx`.
- **Замена VM-менеджера.** `VM_Initialize`, `VM_HandleTLBMiss` и запросы окон ROM через
  `VM_Alloc` должны работать без TLB.
- **Точка входа.** В конфиге не задана: рантайм должен сам выставить стек `0x803FFFC0`
  и вызвать `game_entry`.
